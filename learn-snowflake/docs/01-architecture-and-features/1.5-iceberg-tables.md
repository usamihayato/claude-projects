# Apache Icebergテーブル（分野1.5: Snowflakeストレージ概念の説明）

情報源: https://docs.snowflake.com/ja/user-guide/tables-iceberg

関連ノート: [1.5-micropartitions-and-clustering.md](1.5-micropartitions-and-clustering.md)（テーブルタイプ比較の続き）

## 試験に出るか

公式試験学習ガイド（分野1.5「Snowflakeストレージ概念の説明」）のテーブルタイプ一覧に **Apache Iceberg™** が明記されている。他のテーブルタイプ（永続/Temporary/Transient/外部/ダイナミックテーブル）との違いを問う形式で狙われやすい。

## Apache Icebergテーブルとは

「通常のSnowflakeテーブルのパフォーマンス」と「ユーザー自身が管理する外部クラウドストレージ」を組み合わせたテーブル形式。Apache Icebergというオープンなテーブルフォーマット仕様に準拠しており、**Snowflakeに取り込まずに既存のデータレイクをそのまま活用したい場合**に適している。

## 通常のSnowflakeテーブルとの違い（最重要ポイント）

| 項目 | Icebergテーブル | 通常のSnowflakeテーブル |
|---|---|---|
| ストレージの場所 | 外部クラウドストレージ(S3/GCS/Azure) | Snowflakeマネージド領域 |
| Fail-safe | **なし**(非対応) | あり |
| データ保護・回復の責任 | ユーザー側 | Snowflake側 |
| ストレージ課金 | クラウドプロバイダーが直接請求 | Snowflakeが請求 |
| スキーマ進化 | サポート | 限定的 |

「Fail-safeがない」という点は、[テーブルタイプ比較](1.5-micropartitions-and-clustering.md)の表に加わる重要な差分。Temporary/Transientテーブルも同様にFail-safeがないが、理由は異なる（あちらは「データの重要度が低いため対象外」、Icebergは「ストレージ自体がSnowflake管理外のため」）。

## カタログ管理の2つのモデル

### そもそも「カタログ」とは何か

一般的な「データカタログ」(データ資産の一覧・用語集ツール)とは別物で、Iceberg形式が技術的に必要とする**「今どのメタデータファイルが最新版かを指し示すポインター管理の仕組み」**を指す。

Icebergテーブルは実データを外部ストレージ(S3等)上にファイルとして保存し、書き込みのたびに新しいメタデータファイル(metadata.json)を追加していく(Gitのコミット履歴に近いイメージ)。

```
テーブルの実体(外部ストレージ上)
├── データファイル(Parquet等)          ← 実際の行データ
├── マニフェストファイル               ← どのデータファイルが
│                                        どのスナップショットに属するか
├── マニフェストリストファイル
└── メタデータファイル(metadata.json)  ← スキーマ・パーティション定義・
                                          スナップショット履歴を記録
                                          (書き込みのたびに新版が生成される)
```

そのため「テーブルXの今の最新状態はどのメタデータファイルを見ればよいか」という**「テーブル名 → 現在の最新メタデータファイルの場所」の対応表**を誰かが管理する必要があり、これがカタログの役割。

なお、Snowflakeの「データベース→スキーマ→テーブル」というオブジェクト階層（分野1.3）とは別の概念。あちらはSnowflake内でのオブジェクトの入れ物の階層、こちらはIceberg形式特有のファイル追跡の仕組み。

### 2つのモデル

Icebergテーブルは「誰がメタデータ（テーブルのどのファイルが最新かという情報）を管理するか」で2パターンに分かれる。

| モデル | 「カタログ」の実体 | 特徴 |
|---|---|---|
| **Snowflakeがカタログを管理** | Snowflake自身が対応表を内部で保持・更新 | メタデータポインターを管理し、読み書き両方をフルサポート。ライフサイクル管理もSnowflakeが実施 |
| **外部カタログを使用** | AWS Glue、Databricks Unity Catalog等、Snowflakeの外側にあるシステムが対応表を保持 | 「カタログ統合」経由でSnowflakeが接続し参照するだけ。Snowflake側のサポートは限定的で、ライフサイクル管理は非対応 |

## 外部ボリュームの役割

外部ボリュームは、**SnowflakeとIcebergテーブル用の外部クラウドストレージを接続するアカウントレベルのオブジェクト**。以下を保持する。

- ストレージ場所の識別情報
- IAM(Identity and Access Management)エンティティ
- セキュアな認証情報

分野3.3の「ストレージ統合」と似た役割だが、こちらはIcebergテーブル専用の接続オブジェクト。**複数のIcebergテーブルが1つの外部ボリュームを共有可能**。

## ユースケース

1. 既存データレイクをSnowflakeに取り込まずそのまま活用したい
2. Snowflake以外の複数のコンピュートエンジン(Spark等)ともデータを共有したい
3. 外部ストレージの料金体系を活用してコストを最適化したい
4. Iceberg仕様準拠により他ツールとの相互運用性を確保したい

## 主要な制限事項

| 分類 | 制限内容 |
|---|---|
| トランザクション | 行レベルの等価削除は非対応(通常のSnowflakeテーブルはDELETE文に対応) |
| トランザクション | 複数ステートメントトランザクション非対応 |
| ストレージ | ドットを含むS3バケット名は非対応(例: `my.s3.bucket`) |
| ストレージ | Fail-safe保護なし |
| その他 | 仮テーブル・一時テーブルとしては作成不可、Snowflakeの暗号化機能非対応、外部管理テーブルはクローニング非対応 |

## 請求体系

- **Snowflakeが課金**: 仮想ウェアハウス(コンピュート)使用料、クラウドサービス料金
- **Snowflakeは課金しない**: 外部ボリューム経由のストレージ(クラウドプロバイダーが直接請求)、アクティブバイト数
- クロスリージョン構成では、外部ストレージへのアクセス時にエグレス(データ転送)コストが別途発生する点に注意

## 試験対策チェックリスト

- [ ] Icebergテーブルのデータが外部クラウドストレージに保存されることを理解している
- [ ] Icebergテーブルに Fail-safe がない理由を説明できる
- [ ] Snowflakeがカタログを管理する場合と外部カタログを使う場合の違いを説明できる
- [ ] 外部ボリュームの役割を説明できる
- [ ] Icebergテーブルのストレージ課金がクラウドプロバイダー側で発生することを理解している
- [ ] Icebergテーブルの主要な制限事項（等価削除非対応、クローニング非対応等）を覚えている

## よく出る問題パターン

**Q. Icebergテーブルと通常のSnowflakeテーブルの最も大きな違いは何か？**
→ A. データがSnowflakeマネージドストレージではなく、ユーザー管理の外部クラウドストレージに保存される点

**Q. Icebergテーブルにはどの障害復旧機能が提供されないか？**
→ A. Fail-safe(Time Travelとは異なり、Fail-safeは非対応)

**Q. 外部カタログ(AWS Glue等)でIcebergテーブルを管理する場合、Snowflake側のサポートはどうなるか？**
→ A. Snowflakeがカタログを管理する場合と比べて限定的になり、テーブルのライフサイクル管理は非対応

**Q. Icebergテーブルのストレージコストは誰が請求するか？**
→ A. Snowflakeではなく、外部ボリュームで接続されたクラウドプロバイダー側が直接請求する
