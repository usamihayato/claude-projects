## 1. Snowflake AIデータクラウドの機能とアーキテクチャ（31%）

### 1.1 Snowflakeアーキテクチャの説明と使用

**自己管理型クラウドサービス**
- ハードウェア・ソフトウェアの導入や管理が不要。メンテナンス、アップグレード、チューニングはSnowflake側が対応
- パブリッククラウド専用（オンプレミス不可）

**3層ハイブリッドアーキテクチャ**

```
┌─────────────────────────────────────────┐
│         クラウドサービス層                  │
│  認証・アクセス制御・メタデータ管理・         │
│  クエリのパース/最適化・Horizonカタログ       │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│         コンピュート層(仮想ウェアハウス)      │
│  MPP(大規模並列処理)、SQL実行、Snowpark、    │
│  各ウェアハウスは独立してリソースを使用        │
│  → 他ウェアハウスとパフォーマンス干渉なし      │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│      データベースストレージ層               │
│  共有ディスク型。マイクロパーティションで     │
│  自動分割・圧縮して保存                     │
└─────────────────────────────────────────┘
```

- **ストレージ層**：共有ディスク型アーキテクチャ。すべてのコンピュートノードが中央データリポジトリにアクセス可能
- **コンピュート層**：仮想ウェアハウス＝独立したコンピュートクラスタ。他ウェアハウスとリソースを共有しないためパフォーマンス干渉が起きない
- **クラウドサービス層**：ユーザーリクエストの受付から実行までを統御。セキュリティ、認証、アクセス制御、メタデータ管理を担当

**サポートするテーブル型（用途別）**
| テーブル型 | 用途 |
|---|---|
| Snowflakeテーブル | 列指向圧縮形式。データウェアハウス向け |
| Icebergテーブル | 外部クラウドストレージ(S3/GCS/Azure)管理。データレイク向け |
| ハイブリッドテーブル | インデックスベースのランダムアクセス最適化。トランザクション処理向け |

**Snowflakeエディション比較**

| 機能 | Standard | Enterprise | Business Critical | VPS |
|---|---|---|---|---|
| 基本セキュリティ、SOC 2 Type II | ○ | ○ | ○ | ○ |
| Time Travel拡張（最大90日） | × | ○ | ○ | ○ |
| 顧客管理暗号化キー、プライベート接続 | × | ○ | ○ | ○ |
| PHI/HIPAA対応 | × | × | ○ | ○ |
| 完全隔離環境 | × | × | × | ○ |
| マルチクラスターWH、クエリ高速化、検索最適化 | ○ | ○ | ○ | × |

- 上位エディションは下位の機能を包含して追加機能を積み上げる構成
- **Standard**: バランス重視の入門エディション／**Enterprise**: 高度なセキュリティ＋プライベート接続／**Business Critical**: PHI/HIPAA対応が必要な組織向け／**VPS**: 他アカウントから完全分離された最高セキュリティ環境

### 1.2 Snowflakeのインターフェースおよびツールの使用

- **Snowsight**: SQL/Pythonでの操作、Notebook、Snowpark Python、Streamlitアプリ開発、可視化・ダッシュボード、クエリ監視、コスト管理、Trust Center、ロール/権限管理、共有・Marketplace公開までを担うWeb UI
- **Snowflake CLI**: 開発者向けオープンソースCLI。Streamlit/Native App/Snowpark Container Services/Snowparkの管理、UDF・ステージ操作、Git統合、CI/CD統合に対応
- **VS Code拡張機能**: SQL文の作成・実行、Snowpark Python連携（構文強調・オートコンプリート・デバッグ）、オブジェクトエクスプローラー、Native App開発・デプロイに対応。認証はユーザー名/パスワード、SSO/SAML、キーペア、OAuthに対応

### 1.3 Snowflakeオブジェクト階層およびタイプの区別

```
組織
└── アカウント
    └── データベース
        └── スキーマ
            └── テーブル / ビュー / 関数 / ステージ / ファイル形式 /
                ストアドプロシージャ / パイプ / 共有 / シーケンス / MLモデル / アプリケーション
```

- セッション・コンテキスト変数はパラメーター階層（アカウント→ユーザー→セッション等）と優先順位を持つ

### 1.4 仮想ウェアハウスの構成

**サイズとクレジット消費**
- XS〜6XLの複数サイズ。1サイズ上がるごとにクレジット消費が2倍（XS=1クレジット/時、4XL=128クレジット/時）
- 課金は1秒単位（起動時60秒分は最低課金）
- ウェアハウスを大きくしても常にロード性能が上がるわけではない（ロードはファイル数・サイズに依存）

**自動一時停止・自動再開**
- デフォルトで両方有効。無操作が続くと自動停止し、次のステートメント送信で自動再開
- マルチクラスターでは「最小クラスター数まで縮小し、かつ無操作」の場合のみ自動停止

**ユースケース別構成**
| ユースケース | 推奨 |
|---|---|
| アドホッククエリ（開発/テスト） | XS〜M。同種のクエリをまとめて実行 |
| データロード | ロードするファイル数・サイズに応じて調整 |
| BI/レポーティング | 本番大規模運用ではL以上が費用対効果良好。Snowsight自体はXSで十分 |

**スケーリング戦略（Enterprise以上）**
- **スケールアップ/ダウン（サイズ変更）**: 単一の複雑なクエリの高速化に有効
- **スケールイン/アウト（マルチクラスター）**: 同時実行数増加によるキューイング解消に有効

**マルチクラスターウェアハウスのスケーリングポリシー**
| ポリシー | スケールアウト条件 | スケールイン条件 |
|---|---|---|
| Standard（既定） | クエリがキューに入った、またはリソース不足と推定時 | 低負荷が続くとアイドルクラスターを1つずつ停止 |
| Economy | 6分間ビジー状態を維持できる負荷がある場合のみ | 残り作業が6分未満と推定時に最も負荷の低いクラスターを停止 |

- 最大化モード（最大=最小）は全クラスター同時起動の静的配分、自動スケールモード（最大>最小）は負荷に応じた動的な起動・停止

**ベストプラクティス**
- 自動一時停止: タスク系は即時、DevOps/DataOps系は約5分、BI/SELECT中心は最低10分（後述4.3のキャッシュ維持と関係）
- ウェアハウス一時停止でローカルディスクキャッシュは消去される

### 1.5 Snowflakeストレージ概念の説明

> 詳細ノート: [01-architecture-and-features/1.5-micropartitions-and-clustering.md](01-architecture-and-features/1.5-micropartitions-and-clustering.md)、[01-architecture-and-features/1.5-iceberg-tables.md](01-architecture-and-features/1.5-iceberg-tables.md)

**マイクロパーティション**
- 1パーティションは非圧縮で50〜500MB。挿入/ロード順にSnowflakeが自動的に透過的に分割（ユーザー管理不要）
- 列指向で保存されるため必要な列のみを効率的にスキャン可能
- 均一に小さいサイズを保つことでデータスキュー（偏り）を回避

**データクラスタリングとプルーニング**
- データ挿入時に各マイクロパーティションのクラスタリングメタデータ（値の範囲等）が自動記録される
- クエリはこのメタデータを使い、不要なマイクロパーティションをスキャンせず絞り込む（プルーニング）
- クラスタリングの「深さ」が小さいほど良好。`SYSTEM$CLUSTERING_DEPTH` / `SYSTEM$CLUSTERING_INFORMATION` で監視

**テーブルタイプ比較**

| 項目 | 永続（Standard） | 永続（Enterprise以上） | Temporary | Transient |
|---|---|---|---|---|
| 持続性 | 明示的削除まで | 明示的削除まで | セッション終了まで | 明示的削除まで |
| Time Travel | 0〜1日（既定1日） | 0〜90日 | 0〜1日 | 0〜1日 |
| Fail-safe | 7日 | 7日 | なし | なし |
| ストレージコスト | 高い | 高い | 低い | 中程度 |

**ビュータイプ**
| 種類 | 特徴 | 用途 |
|---|---|---|
| 標準ビュー | 参照都度クエリ実行。ストレージコストなし | 論理的な分離・SQLのモジュール化 |
| マテリアライズドビュー | 結果を物理保存。高速だがストレージ・維持コストが発生 | 頻繁アクセスされるデータセットの高速化 |
| セキュアビュー | 標準/マテリアライズド両方に適用可 | 機密情報保護、ロールベースアクセス制御、セキュアデータ共有 |

### 1.6 AI/MLおよびアプリケーション開発機能の説明

- **Snowflake Cortex**: LLMで非構造化データを理解・応答するAI機能群
  - Cortex AI関数（SQL内でLLM機能）／Cortex Search（セマンティック検索）／Cortex Analyst（自然言語での分析質問応答）／Cortex Agents／Cortex Code
- **Snowflake ML**: 構造化データ向けの従来型MLモデル（ML関数）と、カスタムモデル開発・運用のための総合プラットフォーム（特徴ストア、モデル登録、MLOps）
- **Snowpark**: Python/Java/Scala対応。データをクライアントに転送せずSnowflake内で直接処理。UDFをインラインで作成しサーバー側で自動実行
- **Streamlit in Snowflake**: PythonでダッシュボードやMLアプリを構築。コードはSnowflakeオブジェクトとして保存、RBACでアクセス制御
- **Snowflake Notebook（ワークスペース）**: Jupyter互換のノートブック環境。CPU/GPUの完全管理型コンテナ、Git統合、ネイティブスケジューラー対応
- 設計原則: すべてのAIモデルはSnowflakeのセキュリティ/ガバナンス境界内で実行され、顧客データはモデル学習に使用されない

## 2. アカウント管理およびデータガバナンス（20%）

### 2.1 Snowflakeのセキュリティモデルと原則の説明

**アクセス制御フレームワーク（3モデルの組み合わせ）**
| モデル | 概要 |
|---|---|
| DAC（任意アクセス制御） | オブジェクト所有者が他者へアクセス権を付与 |
| RBAC（ロールベースアクセス制御） | 権限→ロール→ユーザーの経路で付与。Snowflake推奨の主要手法 |
| UBAC（ユーザーベースアクセス制御） | ユーザーへ直接権限付与。セカンダリロール「ALL」設定時のみ考慮 |

**システム定義ロール（試験頻出）**
```
ACCOUNTADMIN（最上位。SYSADMIN + SECURITYADMINを包含）
├── SECURITYADMIN（権限の一元管理。MANAGE GRANTS。USERADMINを継承）
│   └── USERADMIN（ユーザー・ロールの作成専任）
└── SYSADMIN（ウェアハウス・DB作成。カスタムロール階層の頂点）
PUBLIC（全ユーザー・全ロールに自動付与される疑似ロール）
```

**ロールのタイプ**
- アカウントロール（アカウント内の任意オブジェクトにアクセス、セッションで直接アクティブ化可）
- データベースロール（単一DB内のみ。直接アクティブ化不可、アカウントロール経由で使用）
- インスタンスロール／アプリケーションロール（Native App用）／サービスロール

**ロール階層と権限継承**
- 下位ロールを上位ロールに付与すると、上位ロールの保有者は下位の権限を継承する
- 推奨階層: カスタムアカウントロール → データベースロール／SYSADMIN → SECURITYADMIN/USERADMIN
- 注意点: 「ロールの所有者」はそのロールの権限を自動継承しない

**プライマリロール／セカンダリロール**
- プライマリロール: セッションで1つのみアクティブ。オブジェクト作成時の所有権決定に使用
- セカンダリロール: 複数同時アクティブ可。作成以外のSQL操作の権限判定に使用される
- `CURRENT_ROLE()` / `CURRENT_SECONDARY_ROLES()` / `USE ROLE` / `USE SECONDARY ROLES`

**認証方式**: パスキー（推奨）、TOTP、Duo、SSO/SAML、OAuth、キーペア認証。2024年8月以降作成のアカウントは人間ユーザーのMFA登録が既定で必須

**アカウント識別子**
- 推奨形式: `{組織名}-{アカウント名}`（クラウド/リージョンを問わず機能）
- 旧形式（非推奨）: アカウントロケーター＋リージョン情報（例: `xy12345.us-east-2.aws`）

### 2.2 データガバナンス機能とその使用方法の定義

**列レベルのセキュリティ**
- **ダイナミックデータマスキング（DDM）**: マスキングポリシーでクエリ時にプレーンテキストを動的にマスク（例: `CASE WHEN CURRENT_ROLE()='PAYROLL' THEN val ELSE '***MASKED***' END`）
- **外部トークン化**: 外部関数でマスキングポリシーを利用し、常にトークン化状態でSnowflake上に保持。サードパーティのトークン化プロバイダーが必須
- ポリシー管理は集中管理／ハイブリッド／分散管理の3パターンが選択可能。`APPLY`権限で列への設定/解除、`OWNERSHIP`でポリシー自体を管理

**行アクセスポリシー（Enterprise以上）**
- クエリ実行時にセキュアインラインビューを動的生成し、ポリシー式が真と評価された行のみ返す
- マッピングテーブル（例: 営業部長↔担当地域）を使った行フィルタリングが典型パターン
- 行の挿入防止や表示行の更新・削除防止はできない点に注意

**オブジェクトタグ**
- オブジェクトに最大50個、列にも最大50種類のタグを付与可能（キー・バリュー形式）
- 親オブジェクトのタグは子オブジェクトへ自動継承・伝播
- 用途1: タグベースのマスキングポリシーでガバナンス自動化
- 用途2: コストセンタータグでウェアハウス利用をプロジェクト・部門別に集計
- タグ伝播とタグベースマスキングはEnterprise Edition以上が必須

**Trust Center**
- アカウントのセキュリティリスクを評価・監視するスキャナー機能
- スケジュールベース型（定期チェック）とイベント駆動型（プレビュー）
- 調査結果は「違反」（構成の恒常的な問題）と「検出」（一時的なイベント）に分類
- スキャナーパッケージ: Security Essentials（既定）、CIS Benchmarks、Threat Intelligence
- 閲覧には `SNOWFLAKE.TRUST_CENTER_VIEWER`、管理には `SNOWFLAKE.TRUST_CENTER_ADMIN` ロールが必要

**データレプリケーションとフェールオーバー**
- レプリケーション: ソースアカウントから同一組織内の他アカウントへオブジェクトを複製。セカンダリは読み取り専用
- 複製グループ（読み取り専用の複製のみ）／フェールオーバーグループ（昇格により読み書き可能に切替可）
- アカウントオブジェクト複製・フェールオーバーグループはEnterprise以上、ユーザー/ロール/ウェアハウス等の複製はBusiness Critical以上が必須
- REPLICATE/FAILOVER権限は自動複製されないため両アカウントで個別付与が必要

### 2.3 監視およびコスト管理の説明

**リソースモニター**
- ウェアハウスのクレジット消費のみを監視対象（サーバーレス機能やAIサービスはBudgetsで管理）
- クレジットクォータを指定間隔（日/週/月等）でリセット
- アカウントモニター（アカウント全体、1つのみ）／ウェアハウスモニター（個別、複数可、1WHにつき1モニターのみ）
- アクション: 通知＋一時停止（実行中クエリ完了後）／通知＋即時一時停止（実行中クエリをキャンセル）／通知のみ。最低1つのアクションが必須
- ベストプラクティス: 閾値は100%ではなく90%程度に設定してバッファを確保。作成は`ACCOUNTADMIN`ロールのみ

**ACCOUNT_USAGEスキーマ**
| 項目 | ACCOUNT_USAGE | INFORMATION_SCHEMA |
|---|---|---|
| 削除済みオブジェクト | 記録あり | 記録なし |
| データ反映の遅延 | 45分〜3時間 | リアルタイム |
| 保持期間 | 1年（365日） | 7日〜6か月 |

→ 長期トレンド分析・削除済みオブジェクトの追跡には ACCOUNT_USAGE、リアルタイム確認には INFORMATION_SCHEMA

**Budgets**
- アカウント予算（全体）とカスタム予算（特定オブジェクト・タグ付きリソース単位）の2種類
- リソースモニターとの違い: Budgetsは月次の支出予測・通知が主目的（カスタムアクションとしてストアドプロシージャ実行も可能）、リソースモニターはクレジット消費の即時監視・自動停止が主目的

## 3. データのロード、アンロード、および接続（18%）

### 3.1 データのロードおよびアンロードの実行

**ステージの種類**
| 種類 | 参照方法 | 特徴 |
|---|---|---|
| ユーザーステージ | `@~` | 単一ユーザー・複数テーブル向け。ファイル形式オプション設定不可 |
| テーブルステージ | `@%テーブル名` | 単一テーブル・複数ユーザー向け。所有者のみ操作、ロード時の変換不可 |
| 名前付きステージ | 独立オブジェクト | 複数ユーザー・複数テーブル向け。権限管理・所有権移譲が可能（本番推奨） |
| 外部ステージ | - | S3 / GCS / Azure。アーカイブストレージクラス（S3 Glacier等）は直接ロード不可 |

**COPY INTO のエラー処理オプション（ON_ERROR）**
| オプション | 動作 |
|---|---|
| CONTINUE | エラー行をスキップして継続 |
| SKIP_FILE / SKIP_FILE_n | エラー検出（n行以上）でファイル全体をスキップ |
| ABORT_STATEMENT（既定） | エラー検出でロード全体を中止 |

- 主なオプション: `MATCH_BY_COLUMN_NAME`、`TRUNCATECOLUMNS`、`PURGE`、`FORCE`、`FILES`、`PATTERN`
- 検証: `VALIDATION_MODE`（`RETURN_n_ROWS` / `RETURN_ERRORS` / `RETURN_ALL_ERRORS`）

**DMLエラーのログ記録**
- INSERT/UPDATE/MERGEのエラーを操作失敗にせずエラーテーブルへ記録（`ERROR_LOGGING=TRUE`かつセッションの`OPT_OUT_ERROR_LOGGING=FALSE`が必要）
- 通常のCOPY INTOはこの機能の対象外（コンパイル時エラーになる）

**スキーマ検出**
- `INFER_SCHEMA`: ステージ上のParquet/Avro/ORC/JSON/CSVから列定義を検出
- `GENERATE_COLUMN_DESCRIPTION`、`CREATE TABLE ... USING TEMPLATE` と組み合わせて自動テーブル作成が可能

### 3.2 自動データ取り込みの実行

**Snowpipe**
- ファイルがステージで利用可能になり次第ロードするサーバーレスサービス（マイクロバッチ）
- 実装方式: クラウドストレージのイベント通知による自動ロード／REST APIによる手動トリガー（キーペア認証+JWT）
- サーバーレスのため課金は実処理量ベース（ウェアハウス不要）。ロード履歴保持は14日間（COPY INTOは64日間）

**Snowpipe Streaming**
- ファイルステージングを経由せず行単位で直接テーブルへ書き込むリアルタイム取り込み
- スループット最大10GB/s、レイテンシ約5秒、1回限りの配信保証（オフセットトークン）、チャネル内で順序保証
- Kafka、IoT、CDCなどの用途に適する。Java/Python SDK、REST API、Kafkaコネクタで接続

**ストリーム（変更データキャプチャ）**
- テーブルの変更を記録するが、データ自体は保持せずソースのオフセット（トランザクションバージョン）のみ保持
- SELECTのみではオフセットは進まず、DML内で消費されて初めて進む
- メタデータ列: `METADATA$ACTION` / `METADATA$ISUPDATE` / `METADATA$ROW_ID`
- 種類: 標準（デルタ）ストリーム／追加専用ストリーム／挿入専用ストリーム（外部テーブル用）

**タスク**
- サーバーレスタスク（Snowflakeが自動割当、使用量課金）／ユーザー管理型ウェアハウスタスク（明示的にWAREHOUSE指定）
- スケジュール実行（`SCHEDULE`、CRON式）またはストリームによるトリガー実行
- 複数タスクを連結した「タスクグラフ（DAG）」でワークフロー構築
- `SUSPEND_TASK_AFTER_NUM_FAILURES` / `TASK_AUTO_RETRY_ATTEMPTS` で失敗時の挙動を制御

**ダイナミックテーブル**
- 定義したクエリと `TARGET_LAG`（鮮度要件）に基づき自動的にリフレッシュされるテーブル
- ストリーム＋タスクと比較して、依存関係の追跡やスケジューリングを自動化できる宣言的なアプローチ

### 3.3 各種Snowflakeコネクタおよび統合の識別

**ドライバー・コネクタ**
| 種類 | 対応言語 |
|---|---|
| JDBCドライバー | Java |
| ODBCドライバー | 多言語 |
| Pythonコネクタ | Python |
| Node.jsドライバー | JavaScript |
| .NETドライバー | C# |
| Goドライバー | Go |
| PHP PDOドライバー | PHP |

- すべてTLS 1.2以上に対応（多くはTLS 1.3にも対応）

**ストレージ統合**
- 外部クラウドストレージへの認証をSnowflakeのIAMエンティティに委任する仕組み（推奨方式）
- ステージ作成時・ロード時にAWS認証情報を個別に提供する必要がなくなる（AWS IAMロール直接指定は非推奨・廃止予定）

**API統合**
- HTTPS API経由の外部サービス情報を格納するオブジェクト。外部関数（Amazon API Gatewayなど）やGitリポジトリ連携の認証基盤として利用
- `API_ALLOWED_PREFIXES` / `API_BLOCKED_PREFIXES` でアクセス範囲を制御。`CREATE INTEGRATION`権限は既定で`ACCOUNTADMIN`のみ

## 4. パフォーマンス最適化、クエリ、および変換（21%）

### 4.1 クエリパフォーマンスの評価

**クエリプロファイル**
- 実行プランを演算子ノード単位で可視化。各ノードに演算子型・実行時間・詳細が表示される
- 時間の内訳: Processing（CPU）／Disk IO／Network Communication／Synchronization／Initialization

**代表的な問題兆候**
| 兆候 | 確認方法・意味 |
|---|---|
| ストレージへのバイトスピル | メモリに収まらない中間結果がディスクへ退避。リモートディスクへのスピルは特に性能劣化が大きい |
| 非効率なプルーニング | 「スキャンされたパーティション数」が「パーティション総数」に対してごく一部でない場合は非効率 |
| 爆発的な結合 | JOIN演算子が入力より大幅に多いタプルを生成（結合条件不足・デカルト積） |
| キューイング | ウェアハウスのリソース不足でクエリが順番待ちになっている状態 |

**ACCOUNT_USAGEのQUERY_HISTORYビュー**
- クエリ属性（query_id, query_text, query_type等）とクエリ履歴（実行時間、ステータス、エラー内容等）を過去365日分照会可能
- Snowsight標準のQuery Historyページは過去14日分。他ユーザーのクエリ閲覧には`ACCOUNTADMIN`かMONITOR権限が必要
- ワークロード管理のベストプラクティス: 類似ワークロードを同じウェアハウスにグルーピングしてキャッシュ効率とコスト管理を両立

### 4.2 クエリパフォーマンスの最適化

**クエリアクセラレーションサービス（QAS、Enterprise以上）**
- 外れ値クエリの処理の一部を共有コンピュートリソースにオフロードして高速化
- 対象: SELECT / INSERT / CTAS / COPY INTO。大規模スキャン＋フィルターのアドホック分析などに有効
- `ENABLE_QUERY_ACCELERATION=TRUE` で有効化、`QUERY_ACCELERATION_ELIGIBLE`ビューで対象クエリを確認

**検索最適化サービス（Enterprise以上）**
- 「検索アクセスパス」というメタデータ構造をバックグラウンドで維持し、不要なマイクロパーティションをスキップ
- クラスタリングキーと異なり、テーブルの物理的な再配置は行わない（メタデータレベルの最適化）
- 適する用途: ポイントルックアップ、テキスト検索（SEARCH関数/LIKE）、半構造化データの等価検索、地理空間クエリ

**クラスタリングキー**（詳細ノート: [04-performance-query-transformation/4.2-clustering-keys.md](04-performance-query-transformation/4.2-clustering-keys.md)）
- 選定基準: 数TB規模、選択的フィルター/ソートを伴うクエリ、多くのクエリが同じキーの恩恵を受けること
- 選定優先順位: ①SELECT述語で頻出の列 → ②JOIN述語で頻出の列。最大3〜4列、低カーディナリティ→高カーディナリティの順に配置
- 自動再クラスタリング: DML後の劣化をSnowflakeが自動検出・再編成。クレジット消費とストレージコスト増（Time Travel/Fail-safe期間中は旧パーティションも保持）が発生

**マテリアライズドビュー**
- ベーステーブルの挿入時にリフレッシュ、削除時に圧縮をバックグラウンドで自動実行。クエリ結果は常に最新
- 制限: 単一テーブルのみ、自己結合不可、ビュー/テーブル関数/動的テーブル参照不可、UDF・ウィンドウ関数・HAVING・ORDER BY不可、DML直接実行不可、Time Travel非対応

### 4.3 Snowflakeキャッシュの使用

| キャッシュ種別 | 保存場所 | 特徴 |
|---|---|---|
| **クエリ結果キャッシュ** | クラウドサービス層 | 完全一致するクエリを再実行すると即座に結果を返却。既定24時間で失効（100KB超の結果は6時間でアクセストークン失効）。ウェアハウス起動不要でコスト効率が高い |
| **メタデータキャッシュ** | クラウドサービス層 | テーブルに関する統計・情報を保持。有効期限なし、全ユーザーが参照可能 |
| **ウェアハウス（ローカルディスク）キャッシュ** | 各ウェアハウスのSSD | クエリ実行時にアクセスしたテーブルデータをキャッシュ。**ウェアハウス一時停止で完全に消去される** |

**結果キャッシュが再利用される条件**
- 新しいクエリが過去実行分と完全一致（大文字小文字を区別）
- `UUID_STRING`や`RANDOM`など再利用不可な関数を含まない、外部関数を含まない、ハイブリッドテーブルからのSELECTでない
- 対象テーブルデータが変更されていない（変更・再クラスタリング・権限変更等でキャッシュ無効化）

**運用上の指針**: BI/SELECT中心のウェアハウスは自動一時停止を長め（10分以上）にしてローカルディスクキャッシュを維持、タスク処理系は逆に即時停止でコストを抑える（1.4節と関連）

### 4.4 データ変換手法の実行

**半構造化データ（VARIANT型）操作**
- アクセス方法: コロン記法 `src:dealership`、ネスト `src:salesperson.name`、配列 `src:vehicle[0].price`（0始まり）
- 列名は大文字小文字を区別しないが、要素名は区別する。抽出値は文字列相当のため計算時は明示キャスト（例: `::NUMBER`）が必要
- `FLATTEN`関数: 配列要素を個別の行に展開。`LATERAL FLATTEN(INPUT => 列)` の形で使用し、複数連結でネストされた配列も処理可能
- その他: `GET_PATH()`、`PARSE_JSON()`、高階関数（FILTER/REDUCE/TRANSFORM）

**集計関数**
- 複数行を入力し単一行を出力（0行入力でも1行を返す、通常NULL）
- 代表例: `SUM`/`AVG`/`COUNT`/`MAX`/`MIN`/`STDDEV`/`MEDIAN`/`LISTAGG`/`ARRAY_AGG`
- `GROUP BY`との関係: GROUP BYはNULLを含む行もグループとして保持するが、複数列を渡す集計関数はいずれかがNULLの行を除外する

**ウィンドウ関数**
- 構文: `関数名(引数) OVER ([PARTITION BY 列] [ORDER BY 列])`
- ランキング系: `ROW_NUMBER` / `RANK` / `DENSE_RANK` / `LAG` / `LEAD`
- 集計系: `SUM`/`AVG`等をOVER句と組み合わせてパーティション内の移動集計を実現
- 統計・分析系: `CORR`、`REGR_SLOPE`等の回帰関数、`HLL`等の近似関数

## 5. データコラボレーション（10%）

### 5.1 データコラボレーションと保護の説明

**Secure Data Sharing**
- アカウント間でデータベースオブジェクトを共有。共有されたオブジェクトは読み取り専用で、実データはコピー・転送されない（メタデータストア＋サービスレイヤーを利用）
- コンシューマー側はストレージ課金なし。クエリ実行に使うコンピュート（ウェアハウス）のみ課金
- 共有可能: データベース、テーブル、動的テーブル、外部/Icebergテーブル、各種ビュー、Cortex Search Service、UDF、MLモデル 等

**クローニング（ゼロコピークローン）**
- 作成直後はソースデータへの参照のみでストレージを消費しない「ゼロコピー」
- 課金が発生するのはクローン側でデータの変更・追加が行われた差分のみ
- 対象: データベース/スキーマ（再帰的）、各種テーブル、データベースロール、ステージ、ファイル形式、シーケンス、ストリーム、タスク、アラート等（外部テーブル・ハイブリッドテーブルは対象外）

**Time Travel**
| エディション | 保持期間 |
|---|---|
| Standard | 0〜1日（既定1日） |
| Enterprise以上（永続オブジェクト） | 0〜90日 |
| 一時オブジェクト（全エディション） | 0〜1日 |

- `AT`/`BEFORE`句でTIMESTAMP・OFFSET・STATEMENT（クエリID）指定による過去時点の参照・クローンが可能
- `UNDROP`でテーブル/スキーマ/データベース等をDROP実行前の最新状態に復元（同名オブジェクトが存在すると失敗）
- 保持期間経過後のデータはFail-safeに移行しTime Travel操作不可になる

**Fail-safe**
- Time Travel保持期間終了後に開始する、**7日間固定**（変更不可）の障害対応専用期間
- ユーザーは直接アクセス不可。Snowflakeサポート経由の最後の手段としてのみ復旧される
- Temporary/Transientテーブルには適用されない（1.5節のテーブルタイプ比較を参照）

### 5.2 Snowflakeのデータシェアリング機能の説明

- **プロバイダー**: 共有を作成・管理し、権限で詳細なアクセス制御を行うアカウント
- **コンシューマー**: 共有からインポートした読み取り専用データベースを利用するアカウント（共有ごとに1DB）
- **リーダーアカウント**: Snowflakeアカウントを持たない相手にデータ共有するための特別なアカウント。プロバイダーが作成・管理し、発生クレジットの請求責任もプロバイダーが負う。DML操作不可、既定上限20アカウント
- **データクリーンルーム**: 複数アカウント間でデータを公開せず共同分析するプラットフォーム。所有者（1名）／データプロバイダー／分析実行者の3ロールで構成。YAML仕様でコラボレーションを定義し、テンプレート（JinjaSQL）とコードバンドルを用いて分析を実行。データプロバイダー側はEnterprise Edition以上が必須

### 5.3 Snowflakeマーケットプレイスおよびリスティングを使用したデータ共有

- **Snowflake Marketplace**: プロバイダーとコンシューマーをつなぐプラットフォーム（AWS/GCP/Azureでグローバル提供、Azure Government除く）
- プロバイダー側リスティング: 無料リスト（複数コンシューマーへ同時共有）／サンプルリスト（リクエスト対応）／ライブ共有（コピーなしのリアルタイム共有）／有料リスト
- コンシューマー側の利点: サードパーティデータの探索・組み合わせ、パイプライン構築コスト削減、自動更新の享受
- **Native App Framework**: データとビジネスロジック（Streamlit、ストアドプロシージャ、関数等）をアプリケーションパッケージとして他アカウントに配布。Marketplace経由の公開販売（無料/有料）またはプライベートリストでの直接共有が可能

## よく出る問題パターン

**Q. あるウェアハウスのクエリが遅い。クエリプロファイルで「Bytes spilled to remote storage」が大きい場合の対処法は？**
→ A. ウェアハウスサイズを大きくする、またはクエリ/バッチ処理を見直してメモリに収まる単位に分割する

**Q. 1AD/1リージョンでBIダッシュボード用ウェアハウスの自動一時停止をどう設定すべきか？**
→ A. 頻繁なクエリが見込まれる場合は10分以上に設定し、ローカルディスク（ウェアハウス）キャッシュを維持してコストとパフォーマンスのバランスを取る

**Q. 特定ロールにのみ列の実データを見せ、それ以外には常にマスクしたい。適切な機能は？**
→ A. ダイナミックデータマスキング（列レベルセキュリティ）。`CURRENT_ROLE()`を条件にしたマスキングポリシーを適用する

**Q. 大量データを高頻度・低レイテンシで行単位に取り込みたい場合、どの機能を使うべきか？**
→ A. Snowpipe Streaming（ファイルステージングを経由せず直接テーブルへ書き込み、レイテンシは数秒程度）

**Q. ウェアハウスのクレジット消費を、超過時に即座に止めたい場合の機能は？**
→ A. リソースモニターの「通知と即時一時停止（SUSPEND_IMMEDIATE）」アクション（Budgetsは月次の支出予測通知が主目的で即時停止はできない）

**Q. Snowflakeライセンスを持たない取引先に、追加契約なしでデータを渡したい場合は？**
→ A. リーダーアカウントを作成する（課金・管理責任はプロバイダー側が負う）

**Q. DROPしたテーブルを誤って削除したことに気づいた。保持期間内であればどう復元するか？**
→ A. `UNDROP TABLE` を実行する（Time Travel保持期間内のみ有効。保持期間を過ぎている場合はFail-safeとなりユーザーからは復元不可）

**Q. マイクロパーティションのプルーニングが効いているかはどう確認するか？**
→ A. クエリプロファイルで「スキャンされたパーティション数」と「パーティションの合計数」を比較する
