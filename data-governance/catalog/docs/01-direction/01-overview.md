# 方向性の整理資料：区分値カタログ整備

- 作成日：2026-07-21
- ステータス：ドラフト（レビュー前）

## 1. 目標

対象データベースが保持するカタログデータについて、以下を実現するデータ変換・スキーマ・
テーブル設計を確立する。

- 物理名の列名を、人が理解できる論理名（業務名）に対応付ける
- カラムごとに定義された区分値（コード値）を、人が理解できる表示ラベル・説明に対応付ける
- 対応付けの根拠（どのソースコード・設計書・画面のどの情報を使ったか）を後から追跡できる
- 源流システム側の変更を検知し、カタログへの反映をできる限り自動化する

## 2. 背景

現在、データガバナンス高度化を目的として複数のデータ整備対応を推進中であり、本件は
そのうちの1つとして、業務システムで利用されているデータベースのカタログ整備を目的とする。

## 3. 現状の課題

| # | 課題 | 詳細 |
|---|---|---|
| 1 | 列名が物理名のまま | システム都合の物理名（例：`clm_stat_cd` 等）で管理されており、業務名を知らない人が見ても意味が分からない |
| 2 | 値が区分値（コード値） | 実際の値は人が直接理解できる数値・文字列ではなく区分値で格納されており、参照のたびに変換が必要 |
| 3 | 区分値の定義がカラムごとに分散 | 区分値の意味はカラムごとに個別に定義されており、一元管理された対応表が存在しない |
| 4 | 変換情報が対象DB内に存在しない | 対象DBは別システムのDBサーバのデータを変換なしでそのまま受信しているため、区分値の意味情報自体が対象DB側にはない |

## 4. 推進アプローチ

### 4.1 基本方針

区分値・列名の意味情報は、実際に人が利用している「画面あり業務システム」側の
ソースコードや設計書に存在すると考えられるため、これらを収集し、区分値やその関連情報を
機械的に集計・構造化することで、区分値の内容がまとまったカタログテーブルを作成する。

### 4.2 収集対象

- 画面あり業務システムのソースコード（区分値の定義箇所、enum/定数/マスタ参照処理など）
- 同システムの設計書（テーブル定義書、画面設計書、コード値一覧等）
- 必要に応じて画面自体の表示定義（プルダウン等の選択肢定義）

### 4.3 カタログのレイヤー構成（メダリオンアーキテクチャ）

収集した情報の出典を後から辿れるよう、カタログテーブルを以下の3層に分けて構築する。

```
[Bronze]                  [Silver]                  [Gold]
メタ情報付き        →      名寄せ中の        →       区分値・列定義
生データテーブル           中間テーブル                マスタテーブル
（出典・抽出情報を         （重複排除・競合検知・       （確定版。カタログとして
 そのまま保持）             名寄せロジック適用）         利用者・他システムへ公開）
```

- **Bronze層**：収集したソースコード・設計書から抽出した情報を、出典（ファイルパス・
  ドキュメント名・抽出日時等）のメタ情報付きでそのまま格納する。生データを保持することで
  後から抽出ロジックを見直しても再現可能な状態を保つ。
- **Silver層**：Bronze層の複数ソースを突き合わせ、名寄せ（同一列・同一区分値の統合）や
  重複排除、ソース間の内容不一致（競合）検知を行う中間層。
- **Gold層**：Silver層の名寄せ結果をレビュー・確定した、最終的な列定義マスタ・区分値
  マスタ。カタログとして利用者や他システムに公開する層。

この構成により、源流システム側の変更が入った際にも、再収集〜Bronze〜Silverまでを
自動更新し、Gold層への反映（レビュー後の確定）のみ人手を残す運用を想定する。

## 6. 想定ロードマップ（案）

| フェーズ | 内容 |
|---|---|
| Phase 1 | 対象業務システムのソースコード・設計書の収集範囲確定、収集 |

| Phase 3 | Silver層構築、名寄せ・競合検知ロジックの実装 |
| Phase 4 | Gold層構築、レビュー運用の確立、カタログとしての公開 |
| Phase 5 | 源流システム変更検知〜自動反映の仕組み化 |
