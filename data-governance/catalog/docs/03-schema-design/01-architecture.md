## 1. 全体構成図

```
┌───────────────────────────────────────────────────────────────────┐
│ 収集対象（画面あり業務システム）                                    │
│   ・ソースコード（enum / 定数 / ORMマッピング 等）                 │
│   ・設計書（テーブル定義書 / コード値一覧 / 画面設計書）            │
│   ・画面定義（プルダウン等の選択肢定義）                            │
│   ・コードマスタ(Excel)（業務側で保守されるコード値一覧表）        │
└───────────────────────────────────────────────────────────────────┘
                 │  収集・機械的抽出（定期実行）
                 ▼
┌───────────────────────────────────────────────────────────────────┐
│ Bronze層（RAW）                                                    │
│   メタ情報（出典・抽出日時・抽出バッチID）付きの生データテーブル    │
│   ・RAW_COLUMN_DEFINITION      列名定義の抽出結果                  │
│   ・RAW_CODE_VALUE_DEFINITION  区分値定義の抽出結果                │
└───────────────────────────────────────────────────────────────────┘
                 │  名寄せ・重複排除・競合検知
                 ▼
┌───────────────────────────────────────────────────────────────────┐
│ Silver層（STAGING）                                                 │
│   名寄せ中の中間テーブル（競合フラグ・要確認フラグ・集約元参照）    │
│   ・STG_COLUMN_CANDIDATE       列名対応の名寄せ候補                │
│   ・STG_CODE_VALUE_CANDIDATE   区分値対応の名寄せ候補              │
└───────────────────────────────────────────────────────────────────┘
                 │  レビュー・確定（自動昇格 or 人によるレビュー）
                 ▼
┌───────────────────────────────────────────────────────────────────┐
│ Gold層（MART）                                                      │
│   区分値マスタ・列定義マスタ（版管理あり。カタログとして公開）      │
│   ・DIM_COLUMN_MASTER          列定義マスタ（物理名⇔論理名）        │
│   ・DIM_CODE_VALUE_MASTER      区分値マスタ（コード値⇔表示ラベル）  │
└───────────────────────────────────────────────────────────────────┘
                 │  参照
                 ▼
        対象DBの利用者・他システム（カタログとして参照）
```

## 2. Snowflake上のDB／スキーマ構成

各層をスキーマとして分離し、権限（GRANT）もスキーマ単位で管理する。

```
DATABASE: DG_CATALOG
├── SCHEMA: BRONZE     … RAW_* テーブル一式（収集バッチのみ書き込み可）
├── SCHEMA: SILVER     … STG_* テーブル一式（名寄せ処理バッチのみ書き込み可）
├── SCHEMA: GOLD       … DIM_* テーブル一式（レビュー確定処理のみ書き込み可、
│                          利用者・他システムは参照のみ）
└── SCHEMA: META       … 収集バッチ管理・ソースシステム管理などの運用メタデータ
```

| スキーマ | 役割 | 書き込み主体 | 参照主体 |
|---|---|---|---|
| BRONZE | 抽出した生データの保持 | 収集・抽出バッチ | SILVER変換バッチ |
| SILVER | 名寄せ・競合検知 | 名寄せバッチ | レビュー担当者、GOLD昇格バッチ |
| GOLD | 確定済みカタログ | レビュー確定バッチ | 対象DB利用者、他システム、BIツール等 |
| META | 収集バッチ・ソースシステム管理 | 収集バッチ、運用担当者 | 全バッチ処理（実行制御・ソース管理用） |

## 3. トレーサビリティの担保方法

- Bronze層の各レコードは `RAW_ID` を主キーとして持ち、出典メタ情報を保持する
- Silver層の各レコードは、集約元となった `RAW_ID` の配列（Snowflakeの`ARRAY`型）を
  `SOURCE_RAW_IDS` として保持する
- Gold層の各レコードは、確定根拠となった `STG_ID` （さらに`SOURCE_RAW_IDS`経由で
  `RAW_ID`）への参照を保持する
- 上記の連鎖により、Gold層のある1レコード（例：特定テーブルのある区分値の
  表示ラベル）について「どのソースコード／設計書のどの記述が根拠か」を
  Bronze層まで機械的に遡って特定できる

## 4. 更新・自動反映のデータフロー

```
[収集バッチ]                 (定期実行、例: 週次)
   │ 新規抽出データを追加（既存Bronzeレコードは不変・追記のみ）
   ▼
[Bronze]
   │ 前回バッチとの差分を検出
   ▼
[名寄せバッチ]
   │ 正規化・突合・競合検知
   ▼
[Silver]
   │ 競合／要確認フラグなし → 自動昇格
   │ 競合／要確認フラグあり → レビュー待ちキューへ
   ▼
[Gold]（新バージョンとして追記。既存有効レコードは有効終了日を設定）
```

## 5. 実装基盤の前提（Snowflake AI機能・変換クエリ）

本設計は Snowflake 上での実装を前提とし、以下の点を見据えて整備する。

- 抽出処理（Bronze層への機械的抽出）は、Snowflake Cortex 等のAI機能（ドキュメント解析・
  分類）を活用する前提とする。具体的な実装方式は別途検討する
- Gold層は確定マスタ（テーブル）としてだけでなく、対象DBを直接参照して変換した結果を
  返す変換クエリ・ビューも合わせて成果物に含める（[02-table-definitions.md](02-table-definitions.md)
  5章の参照クエリ例をビュー化したもの等）。利用者が個別にJOINを書かずに済むようにする

## 6. 実データカタログ（実テーブル・列のデータディクショナリ）との関係

区分値マスタ・列定義マスタ（本資料の3層構成）とは別に、対象DBの実テーブル・実列を対象と
した「実データカタログ」（物理列名・日本語論理名・データ型・説明列 等、既存のカタログ
テーブル形式に準拠したデータディクショナリ）を並行して整備する。

- 実データカタログとGold層（`DIM_COLUMN_MASTER`）を突き合わせ、実際に存在するテーブル・
  列についてのみ確定情報として扱う（付け合わせの具体的な運用は今後詰める）
- 実データカタログの形式に合わせ、`DIM_COLUMN_MASTER` に `DATA_TYPE`（データ型）列を追加する
- 区分値を持つ列については、`DIM_CODE_VALUE_MASTER` の現在有効なレコードから
  `コード値: 表示ラベル` 形式の要約文字列を機械的に生成し、`DIM_COLUMN_MASTER.CODE_VALUE_SUMMARY`
  として保持する。生成した要約と説明文（`COLUMN_DESCRIPTION`）は別カラムとして
  保持し、最終的にどちらをどう見せるか（要約のみ／説明文と合成 等）は利用者側の成果物
  選択に委ねる
- 区分値マスタが更新バッチで最新化されるたびに、`CODE_VALUE_SUMMARY` も同一バッチ内で
  再生成する（手動でのコピー・同期作業は発生させない）
- `COLUMN_DESCRIPTION` は `CODE_VALUE_SUMMARY` とは異なり、生成AI（Snowflake Cortex）が
  Bronze層の原文（`SOURCE_RAW_IDS` で紐づく該当列の抽出結果のみ）を根拠に要約生成する。
  Silver層構築までが自動バッチ処理であるため、昇格をブロックする人手レビューは設けず、
  代わりに生成主体・モデルバージョン・生成日時を `DESCRIPTION_GENERATED_BY` /
  `DESCRIPTION_MODEL_VERSION` / `DESCRIPTION_GENERATED_AT` としてGoldまで保持し、事後の
  抜き取り監査（`META.AI_DESCRIPTION_AUDIT_LOG`）で継続的に品質を確認する運用とする。
  詳細ルールは
  [02-data-transformation/01-conversion-policy.md](../02-data-transformation/01-conversion-policy.md)
  4.4節・5.1節を参照

## 7. 実テーブル単位カタログ（テーブル定義書相当）の扱い

「実テーブルごとに列一覧・説明をまとめたカタログ（テーブル定義書のような一覧）」は、
新規のテーブルを追加設計する必要はなく、既存のBronze→Silver→Goldの枠組みでそのまま
表現できる。

- 個別ソース（設計書・ソースコード・画面定義等）から抽出した、あるテーブルについての
  歯抜けの列情報は、通常どおり `BRONZE.RAW_COLUMN_DEFINITION` に格納する
- 複数ソースを組み合わせて歯抜けを埋め、1テーブル分の列情報を完成させる処理は、
  `SILVER.STG_COLUMN_CANDIDATE` の名寄せ処理（[02-data-transformation/01-conversion-policy.md](../02-data-transformation/01-conversion-policy.md)
  4章）がすでに担っている。`STG_COLUMN_CANDIDATE` を `TABLE_PHYSICAL_NAME` でグルーピングして
  参照すれば、そのままテーブル定義書相当の一覧として利用できる
- 確定後は `GOLD.DIM_COLUMN_MASTER` を `TABLE_PHYSICAL_NAME` でグルーピングして参照すれば、
  確定版のテーブル単位カタログとなる
- 複数のBronzeレコードを掛け合わせて1件を完成させる処理は、定義上Silver層の役割である
  （Bronze層は出典1件に対して1件が対応する生データのままとし、他Bronzeレコードとの合成は
  行わない。3章のトレーサビリティ担保・Bronzeの不変性の前提を維持するため）

詳細な抽出ルール・名寄せルール・競合解決ルールは
[02-data-transformation/01-conversion-policy.md](../02-data-transformation/01-conversion-policy.md) を参照。
テーブルごとの列定義は [02-table-definitions.md](02-table-definitions.md) を参照。
