# データ変換方針：区分値・列名カタログの抽出〜名寄せ〜確定ルール

- 作成日：2026-07-21
- ステータス：ドラフト（レビュー前）
- 関連：[01-direction/01-overview.md](../01-direction/01-overview.md)、[03-schema-design/01-architecture.md](../03-schema-design/01-architecture.md)

## 1. 方針の全体像

対象DBには区分値・列名の意味情報が存在しないため、意味情報の「原本」は
画面あり業務システムのソースコード・設計書とする。本方針では、原本から
Bronze → Silver → Gold へ情報を変換していく際の抽出ルール・名寄せルール・
競合解決ルール・更新運用ルールを定める。

## 2. ソース種別と優先順位

複数ソースに同一の列・同一の区分値について異なる記載がある場合に備え、
採用優先順位をあらかじめ定義する。

| 優先度 | ソース種別 | 理由 |
|---|---|---|
| 1（最優先） | 設計書（テーブル定義書・コード値一覧）／コードマスタ(Excel) | いずれも業務側が保守する正式なマスタ情報であるため。両者間で内容が競合する場合は自動採用せず人によるレビュー対象とする |
| 2 | 画面定義（プルダウン等の選択肢定義） | 実際の利用者が目にする表示ラベルであり、実態に最も近いため |
| 3 | ソースコード（enum・定数・マスタ参照処理） | 実装上の事実を反映しているが、コメント表記揺れ等の影響を受けやすいため |

- 優先度は「同一項目に対する記載が競合した場合の採用順」を意味し、収集自体は
  全ソース種別に対して行う（Bronze層には全ソースをそのまま格納する）。
- コードマスタ(Excel)は、主にソースコード単独では拾えない情報（ソースコード側に
  定義自体が存在しない区分値等）を補完する位置づけであり、ソースコードと内容が
  重複した場合はコードマスタ(Excel)側を優先して採用する。
- 優先度の見直しが必要な場合は、本ドキュメントを更新した上でSilver層の
  名寄せロジックに反映する。

## 3. 抽出ルール（原本 → Bronze層）

### 3.1 列名（物理名 → 論理名）の抽出

| ソース種別 | 抽出方法 |
|---|---|
| 設計書 | テーブル定義書のシート内、物理名列・論理名列（日本語名列）をペアで抽出 |
| ソースコード | クラス／DTO のフィールド定義に付随するコメント、ORMのマッピング定義（物理列名⇔プロパティ名）を抽出 |
| 画面定義 | 画面上のラベル文言と、紐づくバインド先の物理名を抽出 |

### 3.2 区分値（コード値 → 表示ラベル）の抽出

| ソース種別 | 抽出方法 |
|---|---|
| 設計書 | コード値一覧シート（コード値・表示名・説明の一覧）をそのまま抽出 |
| ソースコード | enum定義、`switch`/`if`によるコード値分岐、定数マップ（コード値→表示文言）を抽出 |
| 画面定義 | プルダウン・ラジオボタン等の選択肢定義（value属性・表示文言のペア）を抽出 |
| コードマスタ(Excel) | コード値マスタのシートから、コード値列・表示ラベル列（説明列があれば説明列も）をペアで抽出する。対象テーブル物理名・列物理名との対応がシート内に明記されている場合はそれを用い、明記されていない場合は設計書等と突き合わせて補完する |

コードマスタ(Excel)は他ソースと異なり、収集元の時点で既に名寄せ済みの単一マスタで
あることが多い。そのため、あるテーブル・列の組み合わせについてコードマスタ(Excel)が
唯一のソースとなる場合は、Silver層で競合が発生せず、既存の自動昇格ルール（5章）に
従ってほぼそのままGold層へ昇格する。区分値マスタ（`GOLD.DIM_CODE_VALUE_MASTER`）とは
別建てのGoldテーブルを新設する必要はなく、既存のBronze→Silver→Goldの枠組みの中で
この「ほぼ素通しの昇格」を扱える。

同一の物理名列であっても、同じ行にある別の判別列（商品種別コード・国コード等）の値に
よって区分値の意味が変わるケースがある（詳細は7章を参照）。
このような判別列が原本から確認できる場合は、判別列の物理名・値も合わせて抽出し、
`CONTEXT_COLUMN_NAME_RAW` / `CONTEXT_VALUE_RAW` としてBronze層に格納する。判別列の有無は
事前に洗い出せている必要はなく、判別列が確認できない場合は両項目とも `NULL`（＝共通）とする。

抽出処理（設計書・ソースコード・画面定義・コードマスタ(Excel)の解析）は、Snowflake Cortex
等のAI機能（ドキュメント解析・分類）を活用する前提で実装する。具体的な実装方式は別途検討する。

### 3.3 Bronze層格納時の必須メタ情報

抽出した情報は、後からトレース可能なように、必ず以下のメタ情報を付与してBronze層に格納する。

- 出典種別（設計書／ソースコード／画面定義／コードマスタ(Excel)）
- 出典の識別情報（ファイルパス・リポジトリ名・コミットハッシュ・ドキュメント名・
  ドキュメントバージョン・シート名・行番号 等、取得可能な範囲で）
- 抽出日時・抽出バッチID
- 抽出元の生の内容（変換前の原文。Snowflakeでは `VARIANT` 型で保持）

## 4. 名寄せルール（Bronze層 → Silver層）

### 4.1 名寄せの単位

- 列名の名寄せは「対象テーブル物理名 + 列物理名」を単位に行う
- 区分値の名寄せは「対象テーブル物理名 + 列物理名 + 判別列物理名（なければNULL）+
  判別列の値（なければNULL）+ コード値」を単位に行う

### 4.2 名寄せ処理の流れ

1. 同一キー（4.1の単位）を持つBronzeレコードをグルーピングする
2. グループ内の値（論理名 or 表示ラベル）が完全一致する場合は自動的に1件へ集約する
3. 表記揺れ（全角半角・空白・末尾の「等」「区分」等の付与有無）を正規化した上で
   再度一致判定を行う
4. 正規化後も内容が一致しない場合は「競合（conflict）」として扱い、2章の優先順位に
   従って暫定的に採用候補を決定した上で、競合フラグを立てて人によるレビュー対象とする
5. どのソースにも存在しない、あるいは1ソースにしか存在しない項目は「要確認」フラグを
   立てて人によるレビュー対象とする

### 4.3 Silver層に保持する情報

- 統合後の論理名 or 表示ラベルの候補（競合時は優先順位に基づく暫定採用値）
- 競合フラグ・要確認フラグ
- 集約元となったBronzeレコードのID一覧（トレーサビリティ確保のため）

## 5. 確定ルール（Silver層 → Gold層）

- 競合フラグ・要確認フラグが立っていないレコードは、自動的にGold層へ昇格可能とする
- 競合フラグ・要確認フラグが立っているレコードは、レビュー担当者が採用値を確定した後に
  Gold層へ昇格する
- Gold層のレコードは版管理（有効開始日・有効終了日）を持ち、確定後の上書きではなく
  新バージョンの追加として扱う（履歴を残す）
- Gold層の各レコードには、根拠となったSilver層レコードID（さらに遡ってBronze層
  レコードID）への参照を保持し、最終的な表示ラベルがどのソースのどの記述に
  基づくものかを常に追跡可能とする
- 区分値を持つ列については、`GOLD.DIM_CODE_VALUE_MASTER` の現在有効なレコードから
  `コード値: 表示ラベル` 形式の要約文字列を機械的に生成し、`GOLD.DIM_COLUMN_MASTER.
  CODE_VALUE_SUMMARY` に反映する。生成した要約と人手による説明文（`COLUMN_DESCRIPTION`）
  は別カラムとして保持し、どちらをどう見せるか（要約のみ／説明文と合成 等）は最終成果物の
  利用者側の選択に委ねる。区分値マスタが更新されるたびに、この要約も同一バッチ内で
  再生成する

## 6. 更新運用（源流システム変更への追従）

1. 対象業務システムのソースコード・設計書は定期的（例：週次）に再収集する
2. 再収集した内容は毎回Bronze層に新規バッチとして追加する（既存データは上書きしない）
3. Silver層の名寄せ処理を再実行し、前回バッチとの差分（追加・変更・削除された
   列名・区分値）を検出する
4. 差分のうち競合フラグ・要確認フラグが立たないものは自動的にGold層へ反映する
5. 競合フラグ・要確認フラグが立つ差分のみ、レビュー担当者への通知・確認を経てGold層へ反映する

## 7. コンテキスト（判別列）依存の区分値への対応

### 7.1 コンテキストとは

同一テーブル内の同一物理名列であっても、同じ行にある別の判別列（例：商品種別コード、
国コード等）の値によって区分値の意味（表示ラベル）が変わるケースがある。この判別列を
「コンテキスト」と呼ぶ。

### 7.2 抽出・名寄せ・確定への反映

- **抽出時**（3.2）：判別列が原本から確認できる場合は、その物理名・値を
  `CONTEXT_COLUMN_NAME_RAW` / `CONTEXT_VALUE_RAW` として合わせて抽出する。判別列が
  確認できない場合は両項目とも `NULL`（共通）とする。
- **名寄せ時**（4.1）：名寄せの単位に判別列物理名・判別列の値を追加する。`NULL`
  （共通）は「コンテキストによらず全件に適用される定義」として扱う。
- **確定時**（5章）：Gold層（`GOLD.DIM_CODE_VALUE_MASTER`）は判別列物理名・判別列の値を
  キーの一部として保持し、SCD Type2の版管理（`VALID_FROM`/`VALID_TO`）と組み合わせて
  履歴を保持する。

### 7.3 判別列を事前に洗い出せていなくてもよい

判別列は初回収集時点で全て判明している必要はない。当初は判別列なし（共通、
`CONTEXT_VALUE = NULL`）としてカタログ化を開始し、後から判別列の存在が判明した時点で、
判別列物理名・値を指定した区分値定義を追加投入すればよい。スキーマ変更（ALTER TABLE等）
は不要である。

### 7.4 判別列の後発見時の運用ルール

判別列が後から見つかった場合、それまで「共通」として登録されていたラベルは実際には
不正確だった（本当はコンテキストごとに異なっていた）ことになる。この差分は、名寄せ
ロジック上の「単なる矛盾（表記揺れ等）」とは区別して扱う。

1. 判別列の発見は「重要な仕様変更の検知」として扱い、自動昇格の対象にはしない
  （`NEEDS_REVIEW_FLAG` を強制的に立てる）
2. レビュー担当者が判別列・コンテキスト別のラベルを確認し、確定させる
3. Gold層では、既存の「共通」レコードの `VALID_TO` を判別列発見日（レビュー確定日）に
  設定して無効化し、判別列・コンテキスト別の新レコードを同日付の `VALID_FROM` で追加する
4. 既存の「共通」レコードは削除せず履歴として残す（過去時点でどのラベルが使われて
  いたかを追跡可能にするため）

## 8. 未確定事項（要調整）

- 優先順位（2章）の妥当性は、実際の対象システムのドキュメント整備状況を確認した上で
  最終決定する
- 正規化ルール（4.2-3）の詳細（表記揺れパターンの網羅）は、実データを用いた検証を通じて
  拡充する
- コンテキスト（判別列）の正規化ルール（判別列自体の値の表記揺れ等）は、実データを
  用いた検証を通じて拡充する
- コードマスタ(Excel)について、既存の区分値マスタ（`GOLD.DIM_CODE_VALUE_MASTER`）へ
  名寄せ対象として統合するか、対象範囲によっては別建てのGoldテーブルとするかは、
  実際のExcelの内容（カバー範囲・粒度・保守状況）を確認した上で判断する
- コードマスタ(Excel)とテーブル物理名・列物理名との対応がシート内に明記されていない
  場合の補完方法（設計書との突き合わせルール）は、実データを確認した上で具体化する
- 対象DBの実テーブル・実列を対象に並行整備される「実データカタログ」との付け合わせ運用
  （突き合わせ方式・不一致時の扱い）は、実データカタログ側の整備状況を踏まえて具体化する
- 最終成果物（`CODE_VALUE_SUMMARY` と `COLUMN_DESCRIPTION` の見せ方）の選択肢自体の設計は、
  利用者要件を踏まえて別途検討する
- 抽出処理でのAI機能（Cortex等）活用の具体的な実装方式（利用する関数・プロンプト設計等）は
  別途検討する
- 再収集の実行方式（バッチジョブ／CI連携等）は別途、実装方式検討時に確定する
